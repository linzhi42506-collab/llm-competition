## 二、为什么选"独立 conda ROS2 环境"

不能 `sudo apt install`，但比赛必须要 Gazebo + Nav2。可选方案对比：

| 方案 | 结论 |
|------|------|
| Docker / Podman | ❌ 机器上没有安装任何容器运行时 |
| 手动下载 .deb 再 `dpkg -x` 解包 | ⚠ 可行但要手工处理几百个依赖（OGRE、sdformat、ignition…），极其脆弱 |
| **RoboStack（conda-forge 的 ROS2 发行版）** | ✅ **选中**：一条命令装齐 ROS2 Humble + Gazebo Classic 11 + Nav2 + MoveIt + rosbridge，纯用户态、可整目录删除 |
| 源码编译 Nav2 + Gazebo | ❌ Gazebo Classic 源码编译要数小时，且仍缺系统依赖 |

RoboStack 的 ROS2 Humble 使用 **Python 3.12**，与系统 ROS2 的 Python 3.10 不同，
因此**两套环境绝对不能混用**。`06_脚本/env.sh` 里做了两件事保证隔离：

1. 先 `unset` 掉 `ROS_*`、`AMENT_PREFIX_PATH`、`COLCON_PREFIX_PATH` 等变量；
2. 再把 `LD_LIBRARY_PATH` / `PYTHONPATH` / `CMAKE_PREFIX_PATH` 里的
   `/opt/ros/*` 路径**逐条剔除**，最后才 `conda activate` 独立环境。

> 这一步非常关键：不清理的话 `ros2` 会解析到 `/opt/ros/humble/bin/ros2`（Python3.10），
> 而 `rclpy` 却来自 conda（Python3.12），会出现各种莫名其妙的导入错误。

## 三、安装命令（可复现）

```bash
# 1) 创建独立环境（约 11GB，实测下载速度 ~1.4MB/s）
mkdir -p /home/robo/llm_comp/09_ros2_env
CONDA_PKGS_DIRS=/home/robo/llm_comp/09_ros2_env/pkgs \
/home/robo/miniconda3/bin/conda create -p /home/robo/llm_comp/09_ros2_env/ros2humble \
  --override-channels -c robostack-humble -c conda-forge -y \
  ros-humble-desktop ros-humble-gazebo-ros-pkgs ros-humble-navigation2 \
  ros-humble-nav2-bringup ros-humble-slam-toolbox ros-humble-rosbridge-suite \
  ros-humble-foxglove-bridge ros-humble-moveit ros-humble-ros2-control \
  ros-humble-ros2-controllers ros-humble-xacro ros-humble-robot-state-publisher \
  ros-humble-joint-state-publisher-gui ros-humble-cv-bridge ros-humble-vision-opencv \
  ros-humble-image-transport ros-humble-image-transport-plugins \
  ros-humble-teleop-twist-keyboard ros-humble-tf-transformations \
  colcon-common-extensions compilers cmake make ninja pkg-config git

# 2) 补装 gazebo_ros2_control（第一次跑仿真时发现缺，机械臂控制器起不来）
CONDA_PKGS_DIRS=/home/robo/llm_comp/09_ros2_env/pkgs \
/home/robo/miniconda3/bin/conda install -p /home/robo/llm_comp/09_ros2_env/ros2humble \
  --override-channels -c robostack-humble -c conda-forge -y ros-humble-gazebo-ros2-control

# 3) 编译工作空间
source /home/robo/llm_comp/06_脚本/env.sh
cd "$ROS_WS" && colcon build --symlink-install --cmake-args -DCMAKE_BUILD_TYPE=Release
```

## 四、踩过的坑（都已在脚本里修好）

| # | 现象 | 原因 | 解决 |
|---|------|------|------|
| 1 | `Target dependency '/home/robo/llm_comp/01_' does not exist` | 工作空间路径里**有空格**（`01_仿真工作空间`），CMake/rosidl 按空格切分路径 | 目录改名为 `01_dev_ws` |
| 2 | `ros2` 指向 `/opt/ros/humble/bin/ros2`，`rclpy` 导入失败 | 系统 ROS2 环境变量污染 | `env.sh` 里先清理 ROS 变量与路径再激活 conda |
| 3 | `Failed to load plugin libgazebo_ros_state.so: incorrect plugin type` | `gazebo_ros_state` 是 **world 插件**，不能用 `gzserver -s` 加载 | 写进 `competition.world` 的 `<world>` 里 |
| 4 | 话题变成 `/model_states` 而不是 `/gazebo/model_states` | 插件里加了 `<ros><namespace>/</namespace></ros>`，把命名空间覆盖成了根 | 去掉 `<ros>` 标签；同时代码里**两个话题都订阅**以兼容不同构建 |
| 5 | `Failed to load plugin libgazebo_ros2_control.so` | conda 环境缺 `gazebo_ros2_control` | 单独 conda install 补上 |
| 6 | `AttributeError: property 'clients' of Node object has no setter` | `clients` 是 `rclpy.node.Node` 的保留属性名 | 改名为 `state_clients` |
| 7 | Gazebo 启动报 `bind: Address already in use` | 上次测试的 `gzserver` 没退干净 | 用 `ss -ltnp \| grep 11345` 找 PID 后 `kill -9` |
| 8 | `Couldn't parse parameter override rule: '-p question:='` | 启动脚本把**空字符串**题目传给 `-p`，rcl 直接拒绝 | 脚本改为只在题目非空时才追加该参数 |
| 9 | 正常退出时刷一堆 `ExternalShutdownException` 堆栈 | `rclpy.spin` 在 Ctrl+C/SIGTERM 时抛的退出异常没接住 | 所有节点 `main()` 统一捕获 `(KeyboardInterrupt, ExternalShutdownException)` |

## 五、本环境的两个"非标准"之处（写代码时要注意）

1. **Gazebo 的 ROS 话题/服务在根命名空间**：
   本构建里是 `/model_states`、`/set_entity_state`、`/spawn_entity`，
   而不是常见的 `/gazebo/model_states`、`/gazebo/spawn_entity`。
   项目里的 `object_detector`、`record_positions`、`dynamic_obstacles` 已做**双向兼容**。
2. **场景加载较慢**（PAL_office 是大型 mesh），从启动到 `/model_states` 可用大约
   **60~90 秒**。比赛时评分项 1「系统启动」要求场景完全加载，建议**提前启动**。

## 六、如何切回系统 ROS2

```bash
export USE_SYSTEM_ROS=1
source /home/robo/llm_comp/06_脚本/env.sh
```
但系统环境缺 Gazebo / Nav2，只能跑纯 Python 节点（如 `llm_task_parser`、`task_solver`）。
